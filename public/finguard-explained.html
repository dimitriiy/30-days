FinGuard Flow — без магии

Представьте платёж как запрос из браузера. Но здесь недостаточно показать spinner и повторить fetch: ответ может потеряться уже после выполнения операции. Разбираем, где ждать, где сохранять результат и почему повтор не должен повторно двигать деньги.

Исходная архитектура

Нажмите на любой блок

Сплошная линия — вызов/синхронная связь. Пунктир — передача события. На узком экране схему можно прокручивать вправо. Точное направление каждой связи описано под схемой.

Главное различие: FinGuard выдаёт антифрод-вердикт, а не автоматически списывает деньги. Approve означает «проверка разрешила продолжить». Авторизация, capture/списание и возврат — отдельные операции платёжной системы.

Что ломается в исходной системе

Не сам монолит является ошибкой. Ошибка — общий ресурсный бюджет, длинные транзакции, незащищённые повторы и отсутствие управления перегрузкой. Можно начать исправления в одном репозитории, но с раздельными процессами и пулами.

Что схема не доказывает

В SVG показаны две реплики монолита, а в тексте встречается «один сервер». Надёжность зависит от размещения: две реплики на одном физическом узле не защищают от отказа этого узла.

Стрелка от фонового воркера к Bank Core не доказывает наличие команды списания. Дубли антифрод-событий сами по себе не доказывают двойное списание: нужен повтор неидемпотентной денежной команды в платёжном контуре.

На SVG ML Engine показан без связи с обработчиком, не показана вычитка Kafka, а ClickHouse отсутствует. В предлагаемой схеме эти связи — явно обозначенные дополнения, не утверждение о текущей реализации.

Один poison pill обычно стопорит затронутую партицию или обработчик. Падение всей consumer group — возможный эффект конкретного приложения, но не обязательное свойство Kafka.

Исчерпание connection pool означает недоступность соединений для приложения, а не обязательный crash процесса PostgreSQL. Для доказательства crash нужны логи БД.

Что исправлять сначала

  1. Защитить платёжный путь: убрать внешние HTTP из DB-транзакций, задать deadlines, ограничить очереди, разделить UI и обработку платежей.
  2. Защитить повтор: входная идемпотентность, Outbox, Inbox и сверка неопределённого результата.
  3. Ограничить нагрузку: глобальная квота AML, ограничение конкурентности, pause/resume и DLQ.
  4. Проверить ёмкость: исправление паттернов не превращает БД на 2 500 TPS в БД на 12 000 TPS.
  5. Проверить бизнес-правила: допустимость постфактум AML, сегменты fail-open, реальные возможности void/refund у каждого провайдера.

Разберите отказ по шагам

Это причинные сценарии, а не измерение production. «Безопасно» не означает «все платежи обязательно проходят».

Политика деградации

Предлагаемый пример. Порог 50 000 ₽ взят из задания, а не из нормативного требования. Реальные лимиты согласуют риск-команда и compliance.

Недоступно Что делаем Чего не обещаем
Redis Короткий timeout → circuit breaker → локальный ограниченный кэш правил. Low-risk/малые суммы — возможен fail-open; high-risk/крупные — Challenge или Reject. Локальный LRU не заменяет глобальные счётчики и остатки лимитов. Он может быть устаревшим.
PostgreSQL Не подтверждаем новый успешный durable-вердикт без надёжной фиксации. Возвращаем согласованный временный отказ/Challenge. Повтор — с прежним ключом. Нельзя «просто разрешить», если результат и событие нигде надёжно не сохранены. Альтернативный durable log — отдельный дизайн.
AML Fast Path независим. Slow Path: deadline, breaker, ограниченная очередь, приоритеты, TEMPORARY_ERROR или сверка — по типу вызова. При ответе AML за 4 с невозможно выполнить полную эту проверку за 1,5 с.
Kafka / CDC События остаются в Outbox; контролируем возраст Outbox, WAL и свободный диск. После восстановления дочитываем с ограниченной скоростью. Outbox не бесконечен. При превышении допустимого окна риска ограничиваем приём новых платежей.
ClickHouse Платежи не зависят от аналитики. На UI — «данные устарели», время обновления, повтор загрузки. Нельзя выдавать старый экран за live-состояние.
Redis rate limiter Останавливаем внешние AML-вызовы либо используем заранее распределённые консервативные квоты. Локальные bucket по 300 RPS на каждый pod нарушат глобальную квоту.

Как работает отзыв после фрода

  1. Сохраняем FraudDetected и уникальную команду действия в БД/Outbox.
  2. Получаем актуальный статус платежа у провайдера. При неопределённом результате сначала делаем reconciliation.
  3. Если средства только авторизованы и API позволяет отмену — void/cancel. Если уже списаны — инициируем refund. Блокировка карты ограничивает будущие операции, но не возвращает прошлые.
  4. Внешнюю команду отправляем со стабильным Idempotency-Key для конкретного действия, а не с новым ключом на каждый retry.
  5. Timeout после отправки → UNKNOWN_RESULT. Проверяем статус через API/вебхук, не объявляем возврат завершённым заранее.
  6. На UI отдельно показываем «возврат запрошен», «возврат подтверждён», «результат уточняется», «нужна ручная проверка».

Универсальной команды «заморозить уже ушедшие деньги» здесь нет. Для СБП, карт, разных банков и шлюзов возможности и сроки отличаются. Обязательные предварительные санкционные проверки нельзя переносить на постфактум только ради latency.

Transactional Inbox и машина состояний

Inbox — долговечная запись «это событие уже принято, вот его статус». Не путайте её с Redis-флажком. Для финансовой команды нужны уникальность бизнес-операции, история попыток и связь с ответом провайдера.

«Двухфазная обработка» здесь означает короткий захват задачи, внешний вызов без DB-транзакции и короткую фиксацию результата. Это не протокол распределённого коммита 2PC.

Журнал переходов

    Демонстрация в браузере. Здесь нет настоящего Inbox, БД или вызовов банков.

    Таблица допустимых переходов
    Из В Условие
    NEW PROCESSING Атомарный захват, новый fencing token, lease_until.
    PROCESSING COMPLETED Подтверждён результат; запись результата и локального эффекта в одной DB-транзакции.
    PROCESSING TEMPORARY_ERROR Известно, что действие не выполнено, ошибка повторяемая.
    PROCESSING UNKNOWN_RESULT Вызов мог выполниться, но подтверждения нет. Также консервативный исход после истечения lease, если вызов мог начаться.
    TEMPORARY_ERROR PROCESSING Настало next_retry_at, есть квота и retry budget, новый token.
    UNKNOWN_RESULT COMPLETED Сверка подтвердила выполнение.
    UNKNOWN_RESULT TEMPORARY_ERROR Сверка надёжно подтвердила отсутствие эффекта; повтор разрешён.
    PROCESSING FAILED Окончательный известный отказ. Не путать с неизвестным исходом.
    COMPLETED / FAILED Тот же статус Дубликат: возвращаем сохранённый результат, не выполняем эффект ещё раз.
    Как выглядит атомарный захват в SQL

    Упрощённый пример для PostgreSQL. Уникальность Inbox: (tenant_id, consumer_name, event_id). Отдельно нужна уникальность денежной команды: (tenant_id, operation_id, action_type). 

    -- 1. Регистрация события. Короткая транзакция.
INSERT INTO inbox (tenant_id, consumer_name, event_id,
                   status, fencing_token)
VALUES (:tenant, :consumer, :event, 'NEW', 0)
ON CONFLICT (tenant_id, consumer_name, event_id)
DO NOTHING;

-- 2. Атомарный захват только готовой к работе записи.
UPDATE inbox
SET status = 'PROCESSING',
    fencing_token = fencing_token + 1,
    lease_until = clock_timestamp() + :lease_interval,
    attempt = attempt + 1
WHERE tenant_id = :tenant
  AND consumer_name = :consumer
  AND event_id = :event
  AND (
    status = 'NEW'
    OR (
      status = 'TEMPORARY_ERROR'
      AND next_retry_at <= clock_timestamp()
    )
  )
RETURNING fencing_token;

-- COMMIT. Никакого открытого DB BEGIN на время HTTP.
-- Если RETURNING не вернул строку, задача не захвачена.
-- Внешний вызов — со стабильным ключом бизнес-команды.

-- 3. Фиксация ответа только актуальным владельцем.
BEGIN;
UPDATE inbox
SET status = 'COMPLETED', result = :result, lease_until = NULL
WHERE tenant_id = :tenant
  AND consumer_name = :consumer
  AND event_id = :event
  AND status = 'PROCESSING'
  AND fencing_token = :my_token
  AND lease_until > clock_timestamp();

-- Проверить affected_rows = 1.
-- Только тогда записать локальный эффект и Outbox в этой же TX.
-- При affected_rows = 0 — ROLLBACK и сверка результата.
COMMIT;

    Просроченный PROCESSING нельзя безусловно заново отправлять в банк. Если предыдущий воркер успел отправить команду, новый сначала переводит запись в UNKNOWN_RESULT и сверяет результат. Lease должен покрывать deadline вызова и фиксацию либо безопасно продлеваться.

    Граница fencing: token защищает наши условные обновления БД. Он не отменяет запрос старого воркера в чужом банке. Внешний эффект защищают Idempotency-Key, статус API и reconciliation.

    Порядок событий: T2 пришло раньше T1

    Базовый ключ — tenant_id + account_id, если инварианты действительно относятся к аккаунту. Это не ID мерчанта и не обязательно ID карты: границу порядка нужно выбрать из бизнес-правила.

    1. Храним последнюю применённую версию аккаунта v.
    2. Повтор уже известного event_id отсекает Inbox. Старую версию не применяем повторно; конфликтующие данные проверяем.
    3. event_version = v + 1: применяем переход FSM и обновляем версию атомарно.
    4. event_version > v + 1: сохраняем событие в ограниченный долговечный буфер. Это пропуск версии, а не повод немедленно применить T2.
    5. Ждём ограниченное время, запрашиваем недостающее состояние; при превышении срока — сверка/ручное разрешение.
    6. Для оконных антифрод-правил используем event time, watermarks и политику late events. Это отдельная задача от последовательного применения финансовых команд.

    Внешние вебхуки могут не иметь account-wide event_version. Его нельзя выдумать из timestamp. Тогда нужны правила переходов, версия внутреннего агрегата и чтение актуального статуса у провайдера.

    Random salt разрушает группировку аккаунта. Выделенная очередь изолирует горячий ключ, но не делает одну строго последовательную цепочку бесконечно параллельной. Предварительная агрегация допустима для объединяемых метрик, а не для произвольных денежных команд.

    Расчёты по вводным, не бенчмарк

    Где числа не сходятся

    Асинхронность убирает ожидание из HTTP-ответа, но не создаёт пропускную способность. Если очередь получает больше работы, чем обработчик успевает делать, она растёт.

    Измените нагрузку

    Внешняя квота: 300 RPS глобально. Упрощение: один вызов на отобранную операцию, без retry, без burst, без дополнительных квот и tail latency.

    Результат

    Расчётная производительность = min(300, конкурентность / время ответа). Это верхняя оценка, а не гарантия. Для стабильной очереди нужен запас, а не равенство входа и выхода.

    Бэкенд на языке фронтенда

    Аналогии помогают понять идею, но не заменяют гарантии реализации.

    Что это меняет во фронтенде

    1. Не генерируйте новый ключ на retry. Одна пользовательская операция — один стабильный ключ. Новый осознанный платёж — новая операция.
    2. Timeout не равен «платёж не прошёл». Покажите «уточняем статус» и запросите результат по operation_id.
    3. Не сводите всё к success/error. Отдельно моделируйте Challenge, Processing, Unknown Result, Refund Pending и подтверждённые результаты.
    4. Не делайте optimistic success для денег. Можно оптимистично показать получение команды, но не факт списания или завершённого возврата.
    5. Учитывайте версии обновлений. Поздний ответ старого запроса или старое SSE-событие не должны перезаписывать более новое состояние.
    6. Показывайте свежесть аналитики. «Данные на 12:04:03» точнее, чем вечный зелёный индикатор Live.
    7. Challenge — не технический retry. Это отдельный согласованный шаг подтверждения, например через провайдера.
